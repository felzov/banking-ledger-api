# ADR 0017: Structured logs and request correlation

- Status: Accepted
- Date: 2026-10-23
- Amends: [ADR 0011](0011-audit-trail.md), [ADR 0014](0014-failure-handling-unavailability-cancellation-and-shutdown.md),
  [ADR 0015](0015-database-roles-and-least-privilege.md)

## Context

No logging handler was configured: uvicorn configures only its own loggers, so every
application record (the audit writer's fallback lines, retry warnings, the privilege guard's
CRITICAL lines) reached stderr through Python's last-resort handler, WARNING and above only, as
a bare message without time, level or logger. Nothing tied a log line, an audit event and a
client's request together. `audit_events.request_id` was reserved for this since migration 0004,
and left unwritable by the API (ADR 0015) until it existed.

## Decision

### One JSON object per line

- The lifespan sends every record, the application's and its libraries' (uvicorn, SQLAlchemy),
  through one JSON handler on the root logger, on stderr: `time` (UTC), `level`, `logger`,
  `message` and `request_id`; for an exception, `exc_type` and `traceback`. `LOG_LEVEL`
  (default `INFO`).
- Only a fixed list of extra fields is ever written (the access line's `method`, `path`,
  `status`, `duration_ms`; a rate limit's name). Anything else attached to a record is
  dropped, so a stray `extra=` cannot leak a request body.
- `sqlalchemy.engine` is pinned to WARNING: at INFO it logs statements with their parameters.
- What goes into a message is unchanged (ADR 0013): never a password, a token, a token's
  digest or an email address.
- Standard library only.

### A request id per request

- The outermost middleware generates one per request (UUIDv7, sortable by arrival), keeps it in
  a context variable for the request's duration, and returns it as `X-Request-ID`.
- **Generated by the server, never taken from the client:** a client-chosen id could make
  unrelated requests look related in the logs and the audit trail.
- **Every log line** written while serving the request carries it, including lines of other
  loggers and lines from the Argon2 worker threads (`asyncio.to_thread` copies the context).
- **Every audit event** records it in `request_id`: the audit context captures it when the
  service call begins, so the succeeded, rejected or failed event, and the fallback log line of
  an event that could not be written, all name the same request. Outside a request (a service
  called directly) it is NULL. Migration 0014 grants the runtime group `INSERT` on that column,
  and nothing more.
- **One access line per request** (method, path without the query string, status, duration)
  replaces uvicorn's, which is silenced.

### Errors that escape the application

Starlette's `ServerErrorMiddleware` sits outside every application middleware: it answers an
unhandled exception with the `500` after this middleware has returned, and uvicorn then logs the
traceback. The middleware therefore leaves the id bound when an exception escapes (uvicorn runs
every request in its own task, so it ends with the request), the `500` handler adds the header
from it, and uvicorn's traceback line carries it (tested against a real uvicorn). On every other
outcome the middleware unbinds it.

## Alternatives considered

- **`structlog` or `python-json-logger`:** a dependency for a formatter of about forty lines.
- **Accepting a client's `X-Request-ID`:** useful behind a gateway that sets it; without one, an
  injection channel into the audit trail. Revisit with a trusted gateway.
- **Passing the request id through every service signature:** explicit, but touches every
  service for a value no business rule uses; the context variable carries it to the one place
  that writes it (the audit context) and to the log handler.
- **A uvicorn `--log-config` file:** would make uvicorn's first startup lines JSON too, at the
  price of a file that the image and Compose must ship and pass.

## Consequences

- `make logs` shows JSON lines; one request's lines, and its audit events, are found by its id.
- A client reporting a problem can quote `X-Request-ID`.
- Every audit insert names `request_id`: the application needs migration 0014 (downgrading
  below it makes every audit write fail).

## Known limitations

- uvicorn's first two startup lines ("Started server process", "Waiting for application
  startup") are plain text: they are written before the application's lifespan configures
  logging.
- Log lines are as durable as the process's stderr (ADR 0014): shipping them somewhere
  queryable is the deployment's job.
